Avaliação Composição 2 — Individual

Projeto Prático da C2

API REST completa com Node.js, Express, Prisma, SQLite, Autenticação e Testes

Prezados alunos, esta é a especificação da avaliação prática da Composição 2 (C2), valendo 10,0 pontos. Parte 1

O que você vai construir

Visão geral do produto

Você desenvolverá uma API REST completa em Node.js + TypeScript que sirva como back-end de um sistema de domínio à sua escolha. Sugestões de domínio (escolha um ou proponha outro ao professor):

  • Blog / Rede social — usuários, posts, comentários, curtidas, seguidores.
  • Loja virtual — usuários, produtos, categorias, pedidos, itens de pedido.
  • Biblioteca digital — usuários, livros, autores, empréstimos, reservas.
  • Plataforma de tarefas (To-do) — usuários, projetos, tarefas, etiquetas, colaboradores.
  • Agendamento de serviços — usuários, profissionais, serviços, agendamentos, avaliações.
  • Sistema acadêmico — usuários, disciplinas, matrículas, avaliações, frequência.

Requisito mínimo: pelo menos 3 entidades relacionadas, sendo uma delas o User.

Parte 2

Requisitos técnicos obrigatórios

Stack e arquitetura

  • Runtime: Node.js 20+ com TypeScript (ES Modules).
  • Framework HTTP: Express.js.
  • ORM: Prisma com adapter better-sqlite3.
  • Banco de dados: SQLite (arquivo local versionado via migrations).
  • Autenticação: JWT (jsonwebtoken) + bcrypt para hash de senhas.
  • Autorização: mínimo de 2 papéis (USER, ADMIN) + controle por propriedade.
  • Validação: biblioteca de schema (Zod recomendado) em todas as rotas de escrita.
  • Testes: Vitest + Supertest, com banco de testes isolado.
  • Cobertura mínima: 70% de linhas e funções.
  • Controle de versão: repositório no GitHub com histórico de commits significativo.

Parte 3

Funcionalidades obrigatórias

O que sua API deve oferecer

Autenticação e gestão de usuários:

  • POST /auth/register — cria conta nova (senha hasheada).
  • POST /auth/login — devolve JWT válido.
  • GET /auth/me — retorna dados do usuário autenticado.
  • Senha nunca deve aparecer nas respostas.

CRUD completo para cada entidade:

  • Criar (POST), listar (GET), buscar por id (GET /:id), atualizar (PUT/PATCH), apagar (DELETE).
  • Respostas em JSON com status codes corretos (200, 201, 204, 400, 401, 403, 404, 422).
  • Pelo menos uma rota com relacionamento (include no Prisma).

Regras de autorização:

  • Rotas de leitura pública (se aplicável) e rotas autenticadas.
  • Pelo menos uma operação restrita a ADMIN.
  • Pelo menos uma operação com controle de propriedade (só o dono pode editar/apagar).

Parte 5

Testes obrigatórios

Cenários mínimos que sua suíte deve cobrir

Testes unitários (mínimo 5):

  • Helpers de senha (hash diferente do plain, verify correto/incorreto).
  • Helpers de token (assina e decodifica payload).
  • Validações de schema (Zod) para inputs válidos e inválidos.

Testes de integração (mínimo 10):

  • Registro com sucesso e falha (email duplicado, senha curta).
  • Login com sucesso e falha (credencial inválida).
  • Acesso sem token retorna 401 em rota protegida.
  • CRUD completo de pelo menos uma entidade (criar, ler, atualizar, apagar).
  • Autorização por papel (USER tenta acessar rota ADMIN → 403).
  • Autorização por propriedade (USER tenta editar recurso de outro USER → 403).

Parte 7

Entregáveis

O que enviar via Envio de Trabalhos

  1. Link do repositório público no GitHub contendo todo o código.
  2. README.md com: descrição do domínio escolhido, lista de entidades, instruções de instalação (npm install, prisma migrate, npm run dev), exemplos de requisições (curl ou Postman) e instruções para rodar os testes.
  3. Arquivo .env.example documentando as variáveis necessárias (sem segredos reais).
  4. Print do relatório de cobertura (saída de npm run test:coverage) anexado ao README ou em pasta docs/.
  5. Coleção do Postman/Insomnia (ou um arquivo .http) com requisições de exemplo cobrindo o fluxo de autenticação e CRUD principal.

Parte 8

Cronograma sugerido

Como dividir as ~3 semanas de trabalho

Semana Foco
1 Escolher domínio, modelar entidades no schema.prisma, rodar a primeira migração e implementar o CRUD básico.
2 Adicionar autenticação (register/login), middlewares de auth/authorize, validação com Zod e regras de propriedade.
3 Escrever testes (unitários + integração), atingir 70% de cobertura, polir README e enviar.

Pontos extras (até +1,0)

  • Paginação e filtros em rotas de listagem (?page=1&limit=20&search=...).
  • Soft delete com campo deletedAt em pelo menos uma entidade.
  • Refresh tokens implementados corretamente.
  • CI no GitHub Actions rodando os testes a cada push.
  • Documentação OpenAPI/Swagger exposta em uma rota /docs.

Regras importantes

  • Trabalho individual. Códigos idênticos entre alunos serão considerados plágio e zerados para ambos.
  • Uso de IA é permitido, desde que você compreenda e consiga explicar cada parte do código. Em apresentação oral, perguntas técnicas podem ser feitas.
  • Arquivos .env reais nunca devem ser commitados. O .gitignore deve incluí-los.
  • O repositório deve estar público ou compartilhado com o e-mail do professor.
  • Atrasos: 1,0 ponto por dia, máximo 3 dias. Após, não aceito.
  • Dúvidas podem ser tiradas no Fórum ou diretamente em sala/horário de atendimento.
